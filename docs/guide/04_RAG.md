# 4단계 — RAG: ‘왜 이 권역인가요?’ 설명 · 물어보기

> 원칙 하나: **숫자는 모델(추천 표)에서, 말은 LLM 에서.** LLM 이 숫자를 만들거나 바꾸면 검사에서 잡아 화면에 표시한다.
> 근거가 없으면 없다고 답한다. 수업용 예시 문서는 실제 법령처럼 말하지 않는다.

## 1. 두 가지 쓰임

| | 근거 설명 (explain) | 물어보기 (ask) |
|---|---|---|
| 어디서 | 첫 화면 순위 카드의 ‘왜 이 권역인가요?’ | 머리글 ‘물어보기’ (/ask) |
| 입력 | 품목 · 날짜 · 권역 | 질문 (+ 앞 대화 2번) |
| 숫자 출처 | `<추천>` 블록 = 그날 추천 표의 그 권역 한 줄 (평소 kg · 어제 배수 · 수온 · 근거 · 경고 · Top-3) | 근거 문서에 적힌 숫자만 |
| 문서 | 서비스 설명 3개 (+ ‘점수의 뜻’ 은 늘 포함) | 전체에서 하이브리드 검색 4개 |
| 인용 | `[추천]` · `[service-01_recommend#03]` | `[문서#번호]` |

## 2. 흐름

```
화면 ──POST /api/rag/explain──▶ Spring RagController ──POST /internal/rag/explain──▶ FastAPI
 ▲     (회원 · 1분 5번)              │  NDJSON 을 한 줄씩 그대로 흘려보냄           │ 1. 추천 표에서 <추천> 블록
 │                                   │  마지막 done 줄을 읽어 rag_qa_log 에 저장    │ 2. 서비스 문서 검색 (BM25+TF-IDF, RRF)
 └──── meta · delta… · done · logged ┘  → {"type":"logged","qaId":…} 한 줄 더     │ 3. LLM 스트림 (ollama · openai · claude)
                                                                                   │ 4. 답 검사: 인용 · 숫자
```

이벤트 (한 줄 = JSON 하나)

| type | 내용 |
|---|---|
| `meta` | 쓰는 LLM, 근거 문서 목록, (설명이면) `<추천>` 블록 |
| `notice` | LLM 을 부를 수 없어 ‘근거 문장 모음’으로 바꿔 탈 때의 안내 |
| `delta` | 답 글 조각 — 화면에 써지듯 붙는다 |
| `done` | 전체 답 · 검사 결과 · LLM · 걸린 시간 |
| `logged` | Spring 이 저장한 기록 번호 → ‘도움이 됐어요’ 를 이 번호로 |

## 3. 문서 (ai/rag_docs)

| 갈래 | 문서 | 청크 나누기 |
|---|---|---|
| `service/` | 추천이 하는 일 · 근거 숫자 · 모델 교체 · 자료 출처 — **코드와 같은 사실만** | `## 제목` 마다 |
| `sample/` | U2 수업용 예시: 가상 어촌계 수칙 · 현장 용어 · 적조 · 해파리 발표 예시 | 수칙은 `제N조` 마다, 특보는 통째로 (HTML 태그 제거) |

운영에서는 국가법령 공동활용(`LAW_OC`)으로 받은 법령, 수집한 특보를 같은 모양(`doc_id · kind · title · body`)으로 더한다(U2 1회차).
문서를 바꾸면 관리자 화면에서 ‘RAG 색인’ 작업(`rag_reindex`) → `rag_doc` 표 갱신 + AI 서버 색인 다시 만들기.

## 4. 검색 — 하이브리드

- **BM25** 낱말 검색. 낱말은 Kiwi 형태소 분석으로 자른다 (‘고수온주의보는’ → 고 · 수온 · 주의보).
- **TF-IDF 글자 조각(2~4글자)** — 띄어쓰기 · 조사가 달라도 겹친다.
- 두 순위를 **RRF**(1/(60+순위) 합)로 합친다. 한쪽이 놓친 것을 다른 쪽이 메운다.
- 질의 확장: ‘잘 잡’ → ‘좋은 날 평소’, ‘확률’ → ‘점수’ 처럼 현장 말을 문서 말로 덧붙인다.
- 임베딩(e5)은 모델을 내려받아야 해서 기본에서 뺐다. 문서가 수십 개이고 낱말이 정해진 분야라 이 둘로 충분했다.

## 5. LLM 백엔드

| `LLM_BACKEND` | 준비 |
|---|---|
| `ollama` (기본) | Ollama 설치 → `ollama pull qwen3:1.7b` (한국어가 더 자연스러운 것: `exaone3.5:2.4b`) |
| `openai` | `OPENAI_API_KEY` + `pip install openai` |
| `claude` | `ANTHROPIC_API_KEY` + `pip install anthropic` |
| `mock` | 없음 — 근거 문장 모음(생성하지 않음). 화면에 ‘LLM 없이 근거 문장 모음’ 으로 표시 |

LLM 을 부를 수 없으면(서버 꺼짐 · 모델 없음 · 키 없음) 오류 대신 **근거 문장 모음으로 바꿔 타고** `notice` 로 알린다.
AI 서버 `/health` 의 `rag.llm_status` 에 ‘모델 없음 — ollama pull …’ 처럼 이유가 나온다.

> 이 저장소의 교안 캡처(`docs/captures/phase4`)는 Ollama 를 쓸 수 없는 환경에서 `LLM_BACKEND=mock` 으로 찍었다.
> 강의실 PC 에서 Ollama 를 켜고 `node scripts/capture/capture.mjs 4` 를 다시 돌리면 같은 장면이 LLM 답으로 찍힌다.

## 6. 답 검사

| 검사 | 방법 | 화면 |
|---|---|---|
| 인용 | 답의 `[…#번호]` · `[추천]` 이 실제 근거 목록에 있나 | ✓ 인용이 모두 실제 근거 / ✕ 없는 근거 인용 n개 |
| 숫자 | 답에서 숫자를 뽑아 `<추천>` 블록 · 근거 문서 · 질문에 있는지 | ✓ 숫자가 모두 근거에 있음 / ✕ 근거에 없는 숫자: 2.7 |
| 모름 | ‘제공된 자료에서 찾을 수 없습니다’ 라고 했나 | 자료에 없다고 답함 |

결과는 `app.rag_qa_log`(질문 · 답 · 근거 번호 · 검사 · LLM · 걸린 시간 · 도움 여부)에 남아 답 품질을 주 단위로 볼 수 있다.

## 7. 만나 본 문제

**스트림이 한 번에 왔다.** `StreamingResponseBody`(비동기)로 중계했더니 AI 서버는 조각을 바로 보내는데 Spring 이 끝까지 모았다가
한 번에 보냈다(소켓으로 재 보니 0.49초에 4KB 한 덩어리). AI 서버 쪽 읽기는 조각마다 바로 되는 것을 로그로 확인한 뒤,
중계를 `HttpServletResponse` 에 직접 쓰고 줄마다 `flush()` 하는 동기 방식으로 바꿔 해결했다. 대가: 답이 끝날 때까지 요청 스레드 하나를 쓴다
(질문 제한 1분 5번 · 답 최대 500토큰이라 이 규모에서는 문제 없음).

## 8. API

| 경로 | 누가 | 하는 일 |
|---|---|---|
| POST `/api/rag/explain` `{species, date, area}` | 회원 | 근거 설명 스트림 |
| POST `/api/rag/ask` `{question, history?}` | 회원 | 물어보기 스트림 |
| POST `/api/rag/{qaId}/feedback` `{helpful}` | 그 답을 받은 회원 | 도움이 됐나 |
| GET `/internal/rag/search?q=` (AI 서버) | 내부 | 검색만 — 실습 · 디버그 |
