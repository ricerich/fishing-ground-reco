# 3단계 — 수집 · 재학습 · 자동 교체 · 관리자 화면

> 목표: 새 자료가 쌓이면 **사람 없이** 다시 배우고, 정해 둔 기준을 넘을 때만 모델을 바꾼다.
> 바꾸지 않은 이유도 남긴다. 사람은 화면에서 같은 작업을 손으로 돌리고, 필요하면 되돌린다.

## 1. 누가 무엇을 하나

```
  ┌───────── 화면(:3000) /admin ─────────┐
  │ 개요 · 모델·교체 · 수집 · 작업 기록    │
  └──────────────┬───────────────────────┘
                 │ /api/admin/** (ADMIN 만)
  ┌──────────────▼───────────────────────┐   읽기: reco.v_svc_* 뷰 (모델 · 교체 기록 · 작업 · 수집)
  │ Spring(:8080) AdminController         │   실행: AI 서버에 '요청'만 → job_queue
  │  · 모든 실행 요청을 app.admin_audit 에 │
  └──────────────┬───────────────────────┘
                 │ POST /internal/jobs/{name}  (X-Internal-Token)
  ┌──────────────▼──────────┐       ┌─────────────────────────────────┐
  │ FastAPI(:8000)          │       │ 작업 프로세스 reco.worker       │
  │  job_queue 에 한 줄 INSERT│ ───▶ │  10초마다 queued 하나를 가져감   │
  └─────────────────────────┘       │  + 정해진 시각(APScheduler)       │
                                    │  → reco.jobs.run(name) → job_run │
                                    └─────────────────────────────────┘
```

- **수동 = 자동**: 스케줄 · 관리자 버튼 · 명령줄(`python -m reco.jobs run …`) 모두 같은 함수(`reco/jobs.py`)를 부르고 같은 표(`job_run`)에 남는다.
- 웹 요청 안에서 학습을 돌리지 않는다. 요청은 202 + 요청 번호를 돌려주고, 화면은 1.5초마다 `/api/admin/queue/{id}` 를 읽는다.
- 두 작업 프로세스가 떠도 같은 요청을 두 번 실행하지 않는다 — `UPDATE … SET status='running' WHERE queue_id=? AND status='queued'` 가 1행일 때만 실행.

| 시각 | 작업 | 하는 일 |
|---|---|---|
| 매일 05:00 · 18:30 | `collect_daily` | 위판(최근 7일 다시) · 권역 관측 14곳 · 해상예보 · 낚시지수 → DB |
| 매일 05:40 | `precompute_today` | 오늘 추천을 챔피언 · 규칙 둘 다 계산해 저장 |
| 매일 06:00 | `evaluate_live` | 라벨이 확정된(D+7) 지난 추천 채점 |
| 월요일 03:00 | `retrain_weekly` | 후보 학습 → 같은 창에서 평가 → 조건 5개 → 교체 또는 거절 |

## 2. 수집 — live 와 replay

| | live (운영) | replay (시연 · 수업) |
|---|---|---|
| 언제 | `.env` 에 `DATA_GO_KR_KEY` 가 있고 `DEMO_TODAY` 가 비었을 때 | 그 밖 |
| 무엇 | 실습 P2 수집기 4종으로 OpenAPI 호출 → `data/raw` → 날짜 표 → DB upsert | 받아 둔 원본(`sample_data`)을 다시 적재 |
| 기록 | 성공 · 늘어남(위판이 늦게 채워짐) · 있음 · 실패 | 재생 · 없음(그날 자료 없음) · (선택) 실패 흉내 |

한 번의 시도가 `collect_log` 한 줄이다. 실패를 지우지 않는 이유: **교체 조건 1** 이 이 표의 최근 7일 성공률을 보기 때문이다.
수집이 불안한 주에는 재학습 결과가 좋아 보여도 믿지 않는다.

## 3. 재학습과 교체 조건

```
as_of(작업한 날) ─┐
                 L = 위판 마지막 날        matured_end = L − 7   (라벨은 D+7 에 확정)
  ── 학습 (처음 ~ fit_until) ──┤── 평가 창 8주 ──┤── 아직 라벨 없음 ──┤
                          fit_until      eval_from … matured_end        L
```

평가 창에서 **후보 · 챔피언 · 규칙**을 같은 날짜 묶음(품목 × 날짜)으로 채점한다. 평가한 모델을 그대로 서비스한다(평가 뒤 다시 학습하지 않음).

| # | 조건 | 기준 | 왜 |
|---|---|---|---|
| 1 | 데이터 상태 | 최근 7일 수집 성공률 ≥ 95%, 학습 행 ≥ 직전 모델의 90% | 자료가 빠진 주의 점수는 믿을 수 없다 |
| 2 | 평가일 수 | 품목마다 ≥ 30일 | 며칠 운 좋은 결과로 바꾸지 않는다 |
| 3 | 챔피언 대비 | 차이 ≥ +0.01 **그리고** 부트스트랩 95% 구간 하한 > 0 | ‘조금 높다’가 우연이 아님을 요구 |
| 4 | 규칙 대비 | 후보 P@3 ≥ 규칙(어제 좋았던 곳) | 단순한 규칙보다 못하면 모델을 쓸 이유가 없다 |
| 5 | 품목별 | 어느 품목도 챔피언보다 0.03 넘게 떨어지지 않음 | 평균이 올라도 한 품목 사용자가 손해 보면 안 된다 |

하나라도 미달이면 후보는 `rejected` + 이유 한 줄. 통과하면 챔피언 교체 → 오늘 추천 다시 계산 → AI 서버에 다시 읽기 요청.

## 4. 세 가지 결과를 화면에서 재현하기 (시연)

실제 자료로 매주 재학습하면 후보는 reco_v1 과 **같은 수준**(P@3 0.598 vs 0.598)이라 늘 거절된다. 이것이 옳은 결과다.
교체 장면을 보이려고 ‘챔피언이 약했던 상황’을 시나리오로 만든다. 교체 기록에는 `scenario` 로 남아 운영 기록과 섞이지 않는다.

| 순서 | 관리자 화면에서 | 결과 |
|---|---|---|
| ① | 재학습 실행 | **거절** — 조건 3: 차이 +0.000 [−0.012, +0.012] |
| ② | 시연: 약한 챔피언 실행 | 바다 관측(수온 · 바람 · 계절)만 쓰는 `reco_v0_sea` 가 챔피언 (시험 P@3 약 0.38~0.41) |
| ③ | 재학습 실행 | **교체** — 5개 모두 통과, 차이 +0.183 [+0.129, +0.238] |
| ④ | 모델 · 교체 → reco_v1 → 되돌리기 | reco_v1 복귀 (조건을 거치지 않음, `rollback` 기록) |
| ⑤ | 수집 → 실패 흉내 30% → 수집 실행 | 권역 관측 성공률 86% 안팎 |
| ⑥ | 재학습 실행 | **거절** — 조건 1(데이터 상태) + 조건 3 |

처음 상태로: `ai/.venv/bin/python -m reco.jobs run bootstrap_demo` (시연 수집 기록 · 모델 기록을 지우고 reco_v1 부터)

## 5. 만나 본 문제

**POST 본문이 사라졌다.** Spring 이 AI 서버에 작업을 요청하자 `Invalid HTTP request received`. Java 의 `HttpClient` 는 기본이 HTTP/2 라
`http://` 주소에 `Upgrade: h2c` 헤더를 붙이는데, uvicorn 은 업그레이드 요청의 본문을 버린다. 1단계는 GET 만 써서 드러나지 않았다.
→ `HttpClient.newBuilder().version(HTTP_1_1)` (AiClient). 2단계의 모의 소셜 서버에서 만난 것과 같은 원인이다.

## 6. API

| 메서드 · 경로 | 하는 일 |
|---|---|
| GET `/api/admin/overview` | 챔피언 · 수집 요약 · 최근 작업 · 대기 요청 · 교체 기록 · 실행 가능한 작업 |
| GET `/api/admin/models` · `/models/{version}` | 모델 기록 (조건 5개 · 품목별 · 구간 포함) |
| POST `/api/admin/models/{version}/rollback` | 되돌리기 요청 (거절된 후보는 대상 아님 → 422) |
| GET `/api/admin/collect?failOnly=` | 출처별 성공률 · 수집 기록 |
| GET `/api/admin/jobs` · `/jobs/{runId}` | 작업 기록 · 자세한 JSON |
| POST `/api/admin/jobs/{name}` | 작업 요청 → 202 `{queue_id}` (`collect_daily` 는 `{simulate_fail: 30}` 가능, 시연만) |
| GET `/api/admin/queue/{id}` | 요청 상태 · 끝나면 작업 요약 |
| GET `/api/admin/audit` | 누가 언제 무엇을 실행했나 |
